# AI 使用说明

本项目使用 JoyCode 辅助完成。本文根据实际对话与执行记录整理，区分提交者的个人决定、采用的 AI 技术分析，以及 AI 完成的代码、测试和复核工作。

## AI 在哪些关键地方提供了帮助

- 阅读作业，将目标拆解为持久化受理、异步投递、失败恢复、系统边界和交付说明。
- 比较 Java、Go、PHP/Laravel，以及 PostgreSQL 任务表、SQLite 单实例和独立消息队列等候选方案。
- 分析响应丢失、发送后崩溃、幂等冲突、租约过期和旧 worker 写回等故障窗口。
- 根据确定的方向实现 Java 服务、数据库访问、重试策略、运行脚本、测试与文档。
- 执行真实 PostgreSQL、HTTP/TLS 和进程级故障实验，安排独立 AI 复核，并修正发现的问题。

## 哪些关键决定由提交者作出，以及原因

### 选择更熟悉的 Java

提交者先比较了 PHP 与 Java，随后明确选择 Java，并补充了个人原因：

> 我主要因为对 Java 更熟悉而选择它，也认为这种熟悉度有助于后续扩展和维护。我曾考虑 PHP，因为听说对方企业使用 PHP；最终权衡后，还是优先选择了自己更熟练的 Java。

对方企业使用 PHP 的信息来自提交者听闻，本项目未独立核实。语言选型的主要依据是个人熟悉度与维护预期，不把语言使用比例或未经验证的性能比较当作结论。

### 保持当前 MVP 范围

讨论重试设计时，AI 建议先补充重试收益、积压量和投递延迟等数据，再根据数据调整参数。提交者明确判断这属于后续扩展，当前 MVP 保持现状即可。

这个决定保留了持久化、幂等、有限重试、超时、并发上限、历史查询和故障恢复；新增观测及数据驱动调参留待实际运行需求出现后再评估。接受的限制是当前没有生产容量数据，也不能证明 20 次、24 小时等初始参数最优。

提交者还明确要求：遇到新的重要 tradeoff 时由其取舍，并在实现后要求逐项核对需求、修正问题及解释架构、边界和失败处理。

### 修复时明确接口边界

2026-10-15 的代码复核发现，JDK HTTP client 会丢掉空 query URL 的末尾 `?`。提交者选择保留现有客户端，在入口明确拒绝 `/hook?` 这类输入；没有为这一边界引入新的 HTTP 库。

讨论数据库超时时，AI 最初给出独立的锁等待、SQL 和读取超时初值。提交者纠正了设计顺序：**先确定接口总超时，再给数据库分配剩余预算，并根据正常耗时分布校准**。随后明确选择：完整请求体读取完成后的 5 秒操作预算、预留 100ms 准备响应和 200ms 提交/回滚，保持同步架构。实现让接口中的多次数据库操作共享同一截止时间；本地基线仅作参考，真实运行数据校准仍是后续工作。

## 采用了哪些 AI 建议

下列方案由 AI 提供技术分析，提交者选择采用。表中的依据属于方案分析，不额外编造提交者未陈述的个人背景或独立推导过程。

| 采用的方案 | AI 给出的依据 | 接受的成本与限制 |
| --- | --- | --- |
| PostgreSQL 任务表 | 受理、任务状态、领取与尝试历史可使用同一数据库事务 | 数据库运维、轮询负载及自行维护调度与租约逻辑 |
| 允许重复并有限重试 | 结果不确定时继续争取送达，并限制长期无效消耗 | 下游可能收到重复通知；最终失败需要业务方处理 |
| Spring Boot、Spring JDBC、通用 HTTP 接口 | 复用接入、事务与配置能力，直接检查任务领取 SQL | 框架与配置成本；业务方负责供应商请求构造 |
| 查询与失败重放、API key 和目标白名单 | 完成排障与补偿流程，限定调用方和出站目标范围 | 不覆盖完整生产运维、凭据管理或不可信域名隔离 |

## AI 给过哪些未采纳的建议

**实际未采纳或暂缓的建议：**

- AI 最初在同等熟悉度下略偏向 Go。提交者依据自己的实际熟练度选择了 Java。
- AI 后续建议优先补充运行观测数据，再调优重试。提交者选择暂缓新增观测与调参，理由是这些属于当前 MVP 之后的扩展工作。

**比较后没有进入第一版的候选：**

- PHP/Laravel：提交者因听说对方企业使用 PHP 而考虑，最终仍优先选择更熟练的 Java。
- SQLite、独立消息队列：比较后选择 PostgreSQL 任务表。独立 MQ 会增加组件与状态/消息一致性处理；题目没有给出必须承担这些成本的吞吐量要求。
- 管理 UI、供应商插件系统、全局顺序和跨区域部署：在草案中列为后续能力，提交者采用了第一版暂缓这些能力的范围。

这里区分实际建议与候选比较，不把全部未来能力写成提交者逐条否决过的方案，也不把它们写成已经实现后被删除的功能。对“过度设计”的判断限于当前阶段是否需要承担额外复杂度；语言选择则属于适配性取舍。

## 如何判断和修正 AI 输出

验证重点放在故障行为，而不是只检查正常请求能否返回成功：

- 使用真实 PostgreSQL 检查并发相同 request_id 只创建一条任务，以及调用方隔离。
- 检查领取、尝试历史和结果写回的事务性，以及旧 lease token 不能覆盖新的结果。
- 用本地供应商先接收请求再延迟响应，验证超时重试可能重复送达。
- 实际强制终止并重启打包应用，检查租约恢复；实际停止并重启数据库，检查受理失败与恢复行为。
- 将“HTTP 2xx”“接入幂等”“有限重试”与“外部业务完成”“下游幂等”“保证最终送达”区分开。

| AI 原始实现或判断 | 问题 | 修正与验证 |
| --- | --- | --- |
| 将 SSLException 一律视为永久失败 | 临时 TLS 传输故障也会终止 | 区分临时故障与证书/身份/协议校验错误；`DeliveryTlsTest` 使用真实 TLS 检查 |
| Retry-After 只解析常见 HTTP 日期 | 旧式日期可能被视为无效值，导致提前重试 | 补充解析；`RetryPolicyTest.acceptsObsoleteHttpDatesWithoutRetryingEarly` 检查结果 |
| JSON 入口限制为 2 MiB | 合法的 1 MiB Body 经 JSON 转义后可能被拒绝 | 信封调整为 8 MiB，Body 仍限制 1 MiB；`NotificationApiIT` 检查边界 |
| 只捕获 DataAccessException | 事务建立或提交/回滚异常可能返回默认 500 | 补充异常映射；新增测试修复前 3 项失败，修复后通过；数据库断连实验检查统一脱敏 503 |
| 数据库只有连接池获取超时 | 已获得连接后的表锁、SQL 或提交仍可长期占用线程 | 共享操作预算；真实表锁、连接池耗尽、多 SQL 累计耗时、提交阻塞与恢复测试 |
| 仅用 HttpRequest.timeout 代表一次投递总时限 | JDK 内部重试可能重新开始计时 | 真实 socket 复现后增加外层单调期限；检查超时、中断后连接关闭 |
| URL 只通过 URI 语法验证 | 孤立 UTF-16 代理字符经数据库编码后被静默替换 | 持久化前验证 UTF-8 可编码性，HTTP 与真实数据库检查非法 URL 拒绝和合法 URL 保留 |
| 领取前检查年龄，领取后直接发送 | 领取过程跨过截止线后仍会发送 | 实际领取后推进测试时钟，验证供应商未收到且任务/历史原子失败 |
| 部分明确 TLS 拒绝未分类 | 协议或访问拒绝被当成临时错误反复尝试 | 6 种真实 TLS fatal alert 记录验证永久分类，并保留临时故障恢复检查 |
| 接受空 query URL | 实际请求会丢失末尾 `?` | 按提交者选择返回 `400 empty_query_not_supported`，保留普通 query 和编码字符 |
| HTTP 日期不支持闰秒 | 有效 Retry-After 可能被忽略而提前重试 | 三种日期形式均检查 `23:59:60` 按下一分钟处理 |

前四项属于早期纠错；后七项来自提交者随后要求的 code review，经故障实验核对后，提交者要求修复并在重要取舍处咨询。修复先使用回归用例确认原有错误，再验证修复后结果。代码、测试和实验由 AI 执行，不归因为提交者独立编码或亲自发现。

本轮修复后的独立复核又指出：已中断的线程不应先启动异步 HTTP 再取消。新增测试复现后，补充发送前中断检查；另用可控 future 检查响应完成与取消竞争时的响应流关闭。测试也检查数据库超时后连接池设置恢复、活动借用归零，避免只凭“后续请求成功”推断资源已经释放。

新增数据库故障脚本也经过独立复核：外部 PostgreSQL 环境变量干扰、SIGTERM 不触发清理两项问题被指出后，AI 修正隔离和清理逻辑，并实际验证环境干扰与 SIGTERM/SIGINT 中断场景。
